Operating System Services: User View vs. System Operation

خدمات نظام التشغيل: منظور المستخدم مقابل كفاءة النظام

👤 Services Helpful to the User خدمات موجّهة لخدمة المستخدم

Designed to make solving user computing problems convenient and safe:

تهدف لجعل تنفيذ برامج المستخدمين سهلاً، ملائماً وآمناً:

  • User Interface (UI): CLI (Command-Line Interface / Shell), Batch, and GUI (Graphical User Interface) / Touchscreen. واجهة المستخدم: سطر الأوامر (CLI/Shell)، المعالجة الدفعية (Batch)، والواجهات الرسومية واللمسية (GUI).
  • Program Execution: Ability to load a program into memory, run it, and terminate execution normally or abnormally (error). تنفيذ البرامج: تحميل البرنامج للذاكرة وتشغيله وإنهاؤه بشكل طبيعي أو عند حدوث خطأ.
  • I/O Operations: Facilitating reading/writing to devices and files since users cannot directly touch I/O hardware. عمليات الإدخال/الإخراج: توفير الوصول للملفات والأجهزة الطرفية دون احتكاك مباشر بالعتاد.
  • File-System Manipulation: Reading, writing, creating, deleting, searching files, and directory management. معالجة نظام الملفات: القراءة، الكتابة، الحذف، إنشاء الأدلة، وإدارة الصلاحيات.
  • Communications & Error Detection: Exchanging messages across processes (Shared Memory or Message Passing) and detecting CPU/memory/I/O hardware or software faults. الاتصالات واكتشاف الأخطاء: تبادل البيانات بين العمليات (ذاكرة مشتركة أو تمرير رسائل) ورصد أخطاء العتاد والبرمجيات باستمرار.

⚡ Functions for System Efficiency وظائف لضمان كفاءة تشغيل النظام نفسه

These services exist to optimize hardware utilization and ensure fair sharing among multiple users/processes:

وظائف داخلية تهدف لتعظيم استغلال الموارد والعدالة بين العمليات والمستخدمين:

  • Resource Allocation: Distributing CPU cycles, main memory, file storage, and I/O devices among concurrent processes. توزيع الموارد (Resource Allocation): إدارة وتخصيص دورات المعالج، الذاكرة، وسائط التخزين والأجهزة.
  • Accounting: Tracking and logging which users/processes consume how much and what types of computer resources. المحاسبة والإحصاء (Accounting): تسجيل استهلاك المستخدمين والعمليات للموارد المختلفة ومراقبتها.
  • Protection and Security: Ensuring all access to system resources is controlled and protecting data against unauthorized internal/external access. الحماية والأمن (Protection & Security): التحكم في الوصول لكافة موارد النظام وحمايته من التداخلات غير المصرح بها داخلياً وخارجياً.
📌
Past Exam True/False Trap: Classification of OS Services فخ امتحاني خبيث (تصنيف خدمات نظام التشغيل) Midterm 2019 Q1.6

Midterm 2019 Q1.6: "Program execution and resource allocation are example of operating-system services provides functions that are helpful to the user." ➔ FALSE!
Explanation: While Program Execution is indeed helpful to the user, Resource Allocation belongs to the second category: functions that ensure the efficient operation of the system itself!

سؤال ميدتيرم 2019: "تنفيذ البرامج وتوزيع الموارد كلاهما أمثلة على خدمات نظام التشغيل المفيدة للمستخدم." ➔ خطأ (False)!
التعليل: تنفيذ البرامج (Program execution) يخدم المستخدم فعلاً، أما توزيع الموارد (Resource allocation) فهو وظيفة داخلية هدفها كفاءة تشغيل النظام نفسه واقتسام الموارد، وليس مساعدة المستخدم بشكل مباشر.

System Calls & Application Programming Interfaces (APIs)

استدعاءات النظام (System Calls) وواجهات البرمجة (APIs)

🔌 What are System Calls? ما هو استدعاء النظام (System Call)؟

System Calls provide the programming interface to the services provided by an operating system.

استدعاءات النظام (System Calls) هي الواجهة البرمجية (Programming Interface) الأساسية للوصول إلى الخدمات التي تقدمها نواة نظام التشغيل.

  • Typically written in C or C++, though certain low-level hardware routines may involve assembly code. تُكتب عادةً بلغة C أو C++، مع بعض أجزاء التخاطب المنخفض بلغة التجميع (Assembly).
  • Programs almost never invoke system calls directly; instead, application developers write code using a high-level Application Programming Interface (API). نادراً ما تستدعي البرامج استدعاء النظام مباشرة؛ بل يستخدم المطورون واجهات برمجية عالية المستوى (APIs).

🌐 The 3 Dominant APIs واجهات التطبيقات البرمجية الثلاث الأشهر

Why prefer standard APIs over direct raw system calls?

لماذا نفضل استخدام الـ API على استدعاءات النظام الخام مباشرة؟

  • 1. Win32 API: For Microsoft Windows environments. 1. Win32 API: مخصصة لبيئات نظام تشغيل Windows.
  • 2. POSIX API: For POSIX-based systems (Linux, UNIX, and macOS). Ensures source code portability. 2. POSIX API: للأنظمة المتوافقة مع معيار POSIX (مثل Linux و UNIX و Mac OS X).
  • 3. Java API: For programs executing in the Java Virtual Machine (JVM). 3. Java API: للبرامج التي تعمل داخل آلة جافا الافتراضية (JVM).
  • Key Benefit: Program Portability: An application written using the POSIX API can compile and execute across diverse POSIX operating systems without rewriting low-level kernel system calls. الفائدة الكبرى: قابلية النقل (Portability): الكود المكتوب لمعيار POSIX يعمل ويُترجم عبر مختلف توزيعات Unix و Linux دون تعديل استدعاءات النواة.
💡
Hard Concept Breakdown: The Complete System Call Execution Flow تبسيط مفهوم معقد: مسار تنفيذ استدعاء النظام من البداية للنهاية

How does a simple user call like printf() or read() execute safely inside the OS kernel?

كيف ينتقل استدعاء بسيط مثل printf() أو read() للتنفيذ الآمن داخل النواة؟

1

User Application Invokes API Function

التطبيق يستدعي دالة المكتبة / API

User program calls a standard C library function (e.g., printf()), which internally invokes the corresponding system call wrapper (e.g., write()).

يستدعي التطبيق دالة قياسية (مثل printf()) والتي بدورها تطلب تغليف استدعاء النظام (مثل write()).

2

System Call Interface & Number Mapping

واجهة استدعاء النظام ورقم الاستدعاء

Each system call has a unique assigned integer number. The system-call interface places this number in a designated CPU register (e.g., EAX / RAX).

يرتبط كل استدعاء برقم فريد، وتضع واجهة النظام هذا الرقم في مسجل مخصص بالمعالج (مثل RAX).

3

Software Trap to Kernel Mode

المصيدة البرمجية (Trap) والتحول لوضع النواة

The program executes a software interrupt or trap instruction (e.g., sysenter, syscall, or int 0x80). Hardware changes the Mode Bit from 1 (User) to 0 (Kernel).

يتم تنفيذ أمر مصيدة برمجية (مثل syscall)، فيقوم العتاد بتغيير بت الوضع فوراً من 1 (مستخدم) إلى 0 (نواة).

4

Kernel Dispatch Table Lookup & Return

البحث في جدول النواة والتنفيذ والعودة

The kernel indexes into the System Call Table using the call number, executes the kernel service code, saves the return value, resets the Mode Bit to 1 (User), and returns control to user code.

تبحث النواة في جدول الاستدعاءات برقم الاستدعاء وتنفذ كود الخدمة، ثم تحفظ ناتج العودة وتُعيد بت الوضع إلى 1 ليعود التحكم للبرنامج.

The Three Methods of Passing System Call Parameters

الطرق الثلاث لتمرير المعاملات لاستدعاءات النظام (سؤال الامتحان الأهم)

1️⃣ Method 1: Pass in Registers الطريقة الأولى: التمرير في المسجلات (Registers)

Parameters are written directly into CPU general-purpose registers before executing the trap instruction.

تُكتب المعاملات مباشرة داخل مسجلات المعالج العامة قبل إطلاق أمر المقاطعة البرمجية.

  • Advantage: Fastest and simplest method; no memory accesses required. الميزة: أسرع وأبسط الطرق، ولا تحتاج لقراءة أو كتابة في الذاكرة.
  • Limitation: In many cases, there may be more parameters than available CPU registers. العيب: محدودة بعدد المسجلات الفيزيائية؛ تفشل إذا كان عدد المعاملات كبيراً.

2️⃣ Method 2: Block / Table in Memory الطريقة الثانية: كتلة بيانات أو جدول في الذاكرة

Parameters are placed in a memory block/table, and the starting memory address of that block is passed as a parameter in a single register.

تُخزن جميع المعاملات في كتلة أو جدول داخل الذاكرة (RAM)، ويُمرر عنوان بداية الكتلة في مسجل واحد فقط للمعالج.

  • Advantage: Does not limit the number or size of parameters being passed. الميزة: لا توجد أي قيود على عدد أو حجم المعاملات الممررة.
  • Real-World Use: Standard approach adopted by Linux and Solaris. الاستخدام العملي: هو النهج المعتمد في أنظمة Linux و Solaris.

3️⃣ Method 3: Pushed onto the Stack الطريقة الثالثة: التمرير عبر مكدس البرنامج (Stack)

Parameters are pushed onto the program stack by the user program, and popped off the stack by the operating system kernel.

يقوم برنامج المستخدم بدفع (Push) المعاملات إلى مكدس البرنامج، وتقوم النواة بسحبها (Pop) من المكدس.

  • Advantage: Also does not limit the number or length of parameters. Clean stack-frame alignment. الميزة: لا يضع حداً لعدد المعاملات، وينسجم مع معايير استدعاء الدوال التقليدية.
  • Past Exam Note: Directly validates Midterm 2014 Q1.5: "The program stack can be used to pass a system call parameters..." (TRUE). ملحوظة امتحانية: يؤكد صحة سؤال ميدتيرم 2014: "يمكن استخدام مكدس البرنامج لتمرير معاملات الاستدعاء" (صواب).
📌
Exam Alert: Highest-Yield Essay Question in Course History تنبيه امتحاني: السؤال المقالي الأكثر تكراراً في تاريخ المقرر Midterms 2014, 2019 & 2021 (3 Marks)

Question: "Describe the three methods for passing parameters needed by system calls."
Standard Model Answer for Full Marks (Dr. Khaled Wassif):
a. Pass parameters in registers: Simplest method, but limited if there are more parameters than registers.
b. Block/Table method: Parameters are stored in a block/table in memory, and the starting address of the block is passed as a parameter in a register (Used by Linux & Solaris).
c. Stack method: Parameters can be placed, or pushed, onto the stack by the program, and popped off the stack by the operating system.
(Note: Methods b and c do not limit the number or length of parameters).

نص السؤال: "اذكر واشرح الطرق الثلاث لتمرير المعاملات التي تحتاجها استدعاءات النظام."
الإجابة النموذجية للدرجة الكاملة (من نموذج إجابة د. خالد وصيف):
أ) التمرير في المسجلات (Registers): الأبسط، لكنه يعجز إذا زاد عدد المعاملات عن المسجلات المتاحة.
ب) التمرير عبر جدول/كتلة بالذاكرة (Block or Table in Memory): تُخزن المعاملات في الذاكرة، ويُمرر عنوان بداية الكتلة في مسجل واحد (مطبق في Linux و Solaris).
ج) التمرير عبر المكدس (Stack): يدفع البرنامج المعاملات في المكدس (Push)، وتسحبها النواة (Pop).
(ملحوظة: الطريقتان ب و ج لا تضعان قيوداً على عدد أو حجم المعاملات الممررة).

OS Design Principle: Policy vs. Mechanism

المبدأ التصميمي الأهم: الفصل بين السياسة والآلية

⚙️ Mechanism: "How to do something" الآلية (Mechanism): "كيف ننجز العمل؟"

The fundamental construct or tool provided by the operating system to perform an action.

الأداة أو البنية البرمجية الأساسية التي يوفرها نظام التشغيل لأداء مهمة معينة.

  • Example: The CPU timer hardware mechanism that triggers an interrupt every fixed duration, or the context switch mechanism that saves/restores PCB registers. مثال: عتاد مؤقت المعالج (Timer) الذي يطلق مقاطعة بعد زمن محدد، أو آلية تبديل السياق (Context switch) لحفظ واسترجاع المسجلات.
  • Mechanisms tend to remain stable over long periods and do not change with user preferences. الآليات تتسم بالثبات والاستقرار الطويل ولا تتغير بتغير رغبات المستخدمين.

📜 Policy: "What will be done" السياسة (Policy): "ما الذي يجب فعله؟"

The decision-making rule that determines how the mechanism is configured and utilized.

القاعدة الإدارية أو القرار الذي يحدد كيفية استخدام تلك الآلية وتوجيهها.

  • Example: Deciding which process gets the CPU next (e.g., FCFS, Priority, or Round Robin) or deciding how long the time slice should be. مثال: تحديد أي عملية ستأخذ المعالج تالياً (هل هي الأعلى أولوية أم الأسبق وصولاً؟) وتحديد طول الشريحة الزمنية.
  • The Separation Principle: Separating policy from mechanism provides maximum flexibility. Policies can be modified dynamically or tailored per site without rewriting low-level kernel code. مبدأ الفصل: الفصل التام بينهما يمنح أقصى قدر من المرونة؛ إذ يمكن تغيير القواعد دون الحاجة لإعادة كتابة كود النواة التحتي.
Dimension وجه المقارنة Mechanism (الآلية) الآلية (Mechanism) Policy (السياسة) السياسة (Policy)
Definition Question السؤال الأساسي How to do something? كيف ننجز الأمر؟ What will be done? ماذا سنقرر ونفعل؟
Rate of Change معدل التغير عبر الزمن Rarely changes; built into core OS foundation. نادرة التغير وثابتة مع الزمن. Changes frequently across environments and workloads. شديدة التغير بين بيئة عمل وأخرى ومع مرور الوقت.
Concrete Example مثال تطبيقي Timer hardware interrupt construct. بنية المقاطعة الناتجة عن مؤقت العتاد. Giving each user job 10 milliseconds of CPU time. تخصيص 10 ميلي ثانية لكل عملية مستخدم.

Operating System Structures: Monolithic, Layered & Microkernels

هياكل أنظمة التشغيل: الأحادية، الطبقية، والميكروكنل

🏛️ Monolithic & Layered Systems الأنظمة الأحادية (Monolithic) والطبقية (Layered)

Classical structural paradigms:

النماذج الكلاسيكية لهيكلة النواة:

  • Monolithic Structure (Original UNIX): Everything below the system call interface and above physical hardware is packed into the kernel (file system, CPU scheduling, memory management). Fast execution because everything resides in the same address space, but difficult to debug and modify. الهيكل الأحادي (Monolithic): تُوضع جميع الخدمات الحيوية (إدارة الملفات، الجدولة، الذاكرة) داخل النواة مباشرة في مساحة عنوان واحدة. سريعة جداً لكن خطأ واحد قد يُسقط النظام بأكمله.
  • Layered Approach: OS is divided into $N$ layers built on top of each other. Layer 0 is hardware; Layer $N$ is user interface. Each layer uses functions and services of only lower-level layers. Simplifies debugging and verification, but difficult to define layers cleanly without performance overhead. النهج الطبقي (Layered): يُقسم النظام لطبقات من 0 (العتاد) إلى $N$ (الواجهة). كل طبقة تعتمد حصرياً على الطبقات التي تحتها. يسهل تتبع الأخطاء لكنه يعاني من بطء تراكم الطبقات.

🔬 Microkernel System Structure (Mach, QNX) هيكل النواة الدقيقة (Microkernel)

Radical design: Moves as much functionality as possible from the kernel into User Space!

تصميم ثوري: نقل أكبر قدر ممكن من الخدمات خارج النواة إلى مساحة المستخدم (User Space)!

  • Kernel Minimalism: Kernel retains only absolute bare essentials: minimal process and memory management, plus a communication facility. نواة مصغرة: تحتفظ النواة بالحد الأدنى المطلق: إدارة مبسطة للذاكرة والعمليات، مع قناة اتصال.
  • Communication: User modules (file system, device drivers) communicate with each other using Message Passing via the microkernel! طريقة التواصل: تتواصل وحدات المستخدم (نظام الملفات، تعريفات الأجهزة) مع بعضها عبر تمرير الرسائل (Message Passing) من خلال الميكروكنل!
  • Benefits: Easier to extend, easier to port to new CPUs, vastly more reliable (less code in kernel mode), and more secure. المزايا: سهولة التوسيع، سهولة النقل لعتاد جديد، واعتمادية وأمان أعلى (أي عطل في تعريف جهاز لا يُسقط النواة).
  • Detriment: Performance overhead caused by constant user-to-kernel mode context switching during message passing. العيب الأكبر: انخفاض الأداء بسبب كثرة التبديل بين وضع المستخدم ووضع النواة لنقل الرسائل.

Kernel Architectures Compared

مقارنة شاملة بين بنيات الأنوية المختلفة

Architecture معمارية النواة Services in Kernel Mode الخدمات داخل وضع النواة Inter-Service Communication التواصل الداخلي Primary Advantage الميزة الأساسية Primary Tradeoff العيب الجوهري
Monolithic (الأحادية) Everything (VFS, IPC, Drivers, Scheduler, Memory). كل شيء (الملفات، الشبكات، التعريفات، الذاكرة). Direct function calls in memory. استدعاءات دوال مباشرة في الذاكرة. Maximum execution speed and efficiency. سرعة تنفيذ قصوى وأداء عالٍ جداً. A crash in one driver crashes entire OS. أي خطأ في تعريف جهاز يسقط النظام كاملاً.
Microkernel (الدقيقة) Bare minimum (IPC, low-level scheduling, memory). الحد الأدنى فقط (الاتصال، جدولة منخفضة). Message Passing between user services. تمرير الرسائل (Message Passing). High reliability, fault isolation, modularity. اعتمادية وأمان وعزل للأعطال. Performance overhead from context switches. هدر في الأداء بسبب كثرة التبديل السياقي.
Modules (LKM) (الوحدات) Core kernel dynamically loads modules into kernel space. نواة أساسية تحمل الوحدات ديناميكياً في مساحتها. Known interface calls in kernel space. استدعاء واجهات محددة داخل النواة. Dynamic flexibility without full reboot (Linux/Solaris). مرونة ديناميكية دون إعادة تشغيل الجهاز. Buggy module still runs in kernel mode. الوحدة المعطوبة ما زالت تعمل بوضع النواة.

System Boot, Mobile Architectures & System Programs

إقلاع النظام، أنظمة الهواتف المحمولة والبرمجيات الخدمية

🚀 System Boot Sequence تسلسل إقلاع النظام (System Boot)

How the computer transitions from cold power to a functioning operating system:

كيف ينتقل الحاسوب من حالة انقطاع الطاقة إلى نظام تشغيل كامل يعمل:

  • Reset Vector: Execution begins at a hardcoded, fixed memory address in firmware ROM/EEPROM when power is applied. عنوان البدء الثابت: يبدأ تنفيذ أول تعليمة من عنوان ذاكرة ثابت ومحدد مسبقاً في ذاكرة ROM.
  • Two-Step Booting: ROM firmware code is kept very small. It loads the Boot Block from a fixed disk sector, which then loads the full Bootstrap Loader (e.g., GRUB) into RAM. الإقلاع ثنائي المراحل: كود الـ ROM صغير جداً؛ يقرأ كتلة الإقلاع (Boot Block) من القرص، والتي بدورها تُحمّل برنامج الإقلاع الكامل (مثل GRUB).
  • Kernel Initialization: The bootstrap loader loads the OS kernel image into RAM, initializes memory and processes, mounts the root filesystem, and launches initial system background daemons. تهيئة النواة: يحمل برنامج الإقلاع صورة النواة للذاكرة، ويهيئ الجداول، ويشغل الخدمات الخلفية الأساسية (Daemons).

📱 Mobile Systems: iOS vs. Android أنظمة الهواتف المحمولة: iOS مقابل Android

Modern layered/hybrid mobile operating systems:

الهياكل الهجينة والطبقية لأنظمة الهواتف المعاصرة:

  • Apple iOS: Built on Mac OS X kernel (Darwin). Layers from top to bottom: Cocoa Touch API ➔ Media Layer ➔ Core Services ➔ Core OS. Closed-source, runs natively on ARM. Apple iOS: مبني على نواة Mac OS X. طبقاته: Cocoa Touch ➔ Media ➔ Core Services ➔ Core OS. مغلق المصدر ويعمل على ARM.
  • Google Android: Open-source system developed by Open Handset Alliance. Uses a modified Linux kernel for hardware abstraction and power management. Google Android: مفتوح المصدر ومبني على نواة Linux معدلة لإدارة العتاد وإدارة الطاقة المتقدمة.
  • Android Runtime (ART / Dalvik VM): Java source files are compiled to bytecode, then converted into Dalvik executable format optimized for resource-constrained devices. بيئة تشغيل أندرويد (Dalvik / ART): يُترجم كود Java إلى كود Dalvik تنفيذي مخصص للأجهزة محدودة الذاكرة.

Chapter 2 Key Terms & Exam Glossary

قاموس المصطلحات والمفاهيم الأساسية للفصل الثاني

System Call
استدعاء النظام (System Call)

A programmatic interface providing user applications controlled access to operating system kernel services.

الواجهة البرمجية التي تتيح لتطبيقات المستخدم الوصول المنظم لخدمات نواة نظام التشغيل.

Application Programming Interface (API)
واجهة برمجة التطبيقات (API)

A set of functions and parameters exposed to programmers (Win32, POSIX, Java) ensuring source code portability.

مجموعة الدوال والمعايير التي يتعامل معها المبرمج مباشرة وتضمن سهولة نقل البرامج عبر المنصات.

Microkernel
النواة الدقيقة (Microkernel)

A kernel structure retaining only minimal services in kernel mode, relying on message passing for user-level modules.

معمارية تجعل النواة في أصغر حجم ممكن، وتعتمد على تمرير الرسائل بين الوحدات العاملة بوضع المستخدم.

Mechanism vs. Policy
الآلية مقابل السياسة

Mechanisms determine how to do something; policies decide what will be done. Separating them grants maximum design flexibility.

الآليات تحدد "كيف" يتم العمل، بينما السياسات تحدد "ماذا" سنقرر. فصلهما يمنح مرونة برمجية عظمى.

Loadable Kernel Modules (LKM)
وحدات النواة القابلة للتحميل

Object-oriented components that can be linked and inserted into the running kernel dynamically as needed without rebooting.

أجزاء برمجية قابلة للربط والتحميل داخل النواة أثناء تشغيلها ديناميكياً ودون الحاجة لإعادة التشغيل.

System Programs / Daemons
برامج النظام والخدمات الخلفية

User-level utilities and background services (daemons) providing a convenient development and administrative environment.

أدوات تعمل في وضع المستخدم وخدمات خلفية تبدأ مع الإقلاع لتقديم بيئة تطوير وإدارة متكاملة.
