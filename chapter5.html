Race Conditions & The Critical-Section Problem

حالة التسابق (Race Condition) ومعضلة القسم الحرج

🏁 What is a Race Condition? ما هي حالة التسابق (Race Condition)؟

A situation where several processes access and manipulate the same shared data concurrently, and the outcome of the execution depends on the particular order in which the access takes place.

موقف تصل فيه عدة عمليات متزامنة إلى نفس البيانات المشتركة وتعدلها معاً، بحيث تعتمد النتيجة النهائية على الترتيب الزمني الدقيق لتنفيذ التعليمات.

  • Producer-Consumer Counter Example: If counter++ (3 assembly instructions: load, increment, store) and counter-- (load, decrement, store) interleave, the final value of counter can incorrectly be 4, 5, or 6 instead of the correct 5! مثال العداد: بما أن زيادة العداد ونقصانه تنقسم كل منها لـ 3 تعليمات بلغة الآلة، فإن تداخلهما ينتج عنه قيمة خاطئة (4 أو 6 بدلاً من 5).
  • To prevent race conditions, concurrent processes must be synchronized! لمنع حالة التسابق، يجب مزامنة العمليات المتزامنة وتنسيق وصولها للبيانات.

🛡️ The 3 Critical-Section Requirements الشروط الثلاثة الإلزامية لحل معضلة القسم الحرج

Any valid solution to the critical-section problem MUST satisfy ALL THREE requirements simultaneously:

أي حل مقبول لمعضلة القسم الحرج يجب أن يحقق الشروط الثلاثة معاً بلا استثناء:

  • 1. Mutual Exclusion (الاستبعاد المتبادل): If process $P_i$ is executing in its critical section, then no other processes can be executing in their critical sections. 1. الاستبعاد المتبادل: إذا كانت العملية $P_i$ تنفذ قسمها الحرج، يُمنع منعاً باتاً دخول أي عملية أخرى لقسمها الحرج.
  • 2. Progress (التقدم): If no process is in its critical section and some processes wish to enter, only those processes not in their remainder sections can participate in deciding who enters next, and this selection cannot be postponed indefinitely. 2. التقدم: إذا كان القسم الحرج شاغراً وهناك عمليات ترغب بالدخول، فلا يجوز تأجيل اختيار العملية التالية لأجل غير مسمى.
  • 3. Bounded Waiting (الانتظار المحدود): A bound must exist on the number of times that other processes are allowed to enter their critical sections after a process has made a request and before that request is granted (prevents starvation!). 3. الانتظار المحدود: يجب وضع حد أقصى لعدد المرات التي يُسمح فيها للعمليات الأخرى بالدخول بعد أن تقدمت عملية بطلب، لمنع التجويع (Starvation).
📌
Past Exam True/False Trap: Critical Section Requirements فخ امتحاني خبيث (شروط القسم الحرج) Midterm 2019 Q1.10

Midterm 2019 Q1.10: "Any solution to the critical-section problem must satisfy at least one of three requirements." ➔ FALSE!
Explanation: A valid solution cannot satisfy just "at least one" requirement; it must satisfy ALL THREE requirements: Mutual Exclusion, Progress, AND Bounded Waiting!

سؤال ميدتيرم 2019: "أي حل لمعضلة القسم الحرج يجب أن يحقق على الأقل شرطاً واحداً من الشروط الثلاثة." ➔ خطأ (False)!
التعليل: لا يكفي تحقيق شرط واحد، بل يجب تحقيق الشروط الثلاثة معاً: الاستبعاد المتبادل، والتقدم، والانتظار المحدود!

Peterson's Solution & Hardware Synchronization

حل بيترسون (Peterson's Solution) وتزامن العتاد

🧠 Peterson's Algorithm (2 Processes) خوارزمية بيترسون (لعمليتين $P_i$ و $P_j$)

A software-based solution sharing two variables: int turn; and boolean flag[2];:

حل برمجي كلاسيكي يعتمد على متغيرين مشتركين: turn (الدور) ومصفوفة الأعلام flag[2]:

do { flag[i] = true; turn = j; while (flag[j] && turn == j); /* Critical Section */ flag[i] = false; /* Remainder Section */ } while (true);
  • flag[i] = true signals: "I am ready to enter the critical section." flag[i] = true تعني: "أنا جاهز وأرغب بالدخول."
  • turn = j signals: "I politely offer the turn to process $j$." turn = j تنازل مهذب: "أمنح الدور للعملية الأخرى $j$ أولاً."
  • Mathematical Proof: Satisfies all 3 requirements (Mutual Exclusion, Progress, and Bounded Waiting). مثبت رياضياً: يحقق الشروط الثلاثة كاملة.

⚡ Hardware Instructions (test_and_set & CAS) تعليمات العتاد الذرية (test_and_set و CAS)

Modern CPUs provide special atomic (non-interruptible) hardware instructions:

توفر المعالجات الحديثة تعليمات عتادية ذرية (لا تقبل المقاطعة أثناء تنفيذها):

  • test_and_set(&lock): Reads the old value of lock and atomically sets lock = TRUE, returning the original value. test_and_set: تقرأ القيمة القديمة للقفل وتضبطها على TRUE ذرياً وتعيد القيمة القديمة.
  • compare_and_swap(&lock, expected, new_value): Swaps value to new_value ONLY IF current value equals expected. compare_and_swap: تبدل القيمة فقط إذا كانت مطابقة للقيمة المتوقعة.
  • Exam Caveat: Simple spinlocks using test_and_set or compare_and_swap satisfy Mutual Exclusion and Progress, but DO NOT satisfy Bounded Waiting unless an explicit waiting queue array is programmed! تنبيه امتحاني: الأقفال البسيطة بهذه التعليمات تحقق الاستبعاد والتقدم، لكنها لا تحقق الانتظار المحدود إلا بإضافة مصفوفة انتظار منظمة!

Semaphores: Eliminating Busy Waiting via Queues

السيمافورات: حل مشكلة الانتظار العاطل عبر الطوابير (سؤال الـ 7 درجات)

🔄 The Flaw of Spinlocks (Busy Waiting) عيب أقفال الدوران (الانتظار العاطل Busy Waiting)

A basic semaphore or spinlock executes while (S <= 0) ;, continuously looping on the CPU while waiting for the lock.

في السيمافور البسيط يدور المعالج في حلقة مفرغة while (S <= 0) ; مستهلكاً طاقة المعالج دون جدوى أثناء الانتظار.

  • Wastes enormous CPU cycles that other ready processes could use productively. يهدر دورات المعالج التي تحتاجها العمليات الأخرى الجاهزة.
  • Acceptable only if locks are held for extremely brief moments on multiprocessor systems (spinlocks). مقبول فقط إذا كان وقت الاحتجاز بالغة القصر على أنظمة متعددة المعالجات.

🛑 Implementation with NO Busy Waiting تطبيق السيمافور بدون انتظار عاطل (كود الامتحان النموذجي)

Instead of looping, the process suspends itself using block(), and is later awakened using wakeup():

بدلاً من الدوران، تضع العملية نفسها في طابور انتظار وتعلق تنفيذها بـ block()، وتوقظها عملية أخرى بـ wakeup():

typedef struct { int value; struct process *list; } semaphore; void wait(semaphore *S) { S->value--; if (S->value < 0) { // add this process to S->list; block(); } } void signal(semaphore *S) { S->value++; if (S->value <= 0) { // remove a process P from S->list; wakeup(P); } }
📌
Past Exam Spotlight: 7-Mark Essay Question سؤال امتحاني مقالي ضخم (7 درجات كاملة) Midterm 2019 Q4 & 2021 Q4

Midterm 2019 Q4 (7 Marks): "Show using a code how semaphores solve the critical section problem without busy waiting."
Model Key Analysis:
• Define the semaphore struct containing int value and struct process *list.
• In wait(): Decrement S.value--. If S.value < 0, add invoking process to S.list and call block() (process enters Waiting state, CPU given to another process).
• In signal(): Increment S.value++. If S.value <= 0, remove process $P$ from S.list and call wakeup(P) (moves $P$ from Waiting state to Ready queue).
Notice: When S.value is negative, its magnitude $|S.value|$ equals the exact number of processes waiting on that semaphore queue!

ميدتيرم 2019 سؤال 4 وميدتيرم 2021 سؤال 4: "وضح باستخدام الكود كيف تحل السيمافورات معضلة القسم الحرج دون انتظار عاطل (without busy waiting)."
تحليل الإجابة النموذجية المعتمدة:
• تعريف بنية السيمافور (struct) بحيث تحوي عداداً value وقائمة مؤشرات للعمليات المنتظرة *list.
• دالة wait(): تنقص العداد S.value--، فإذا أصبح سالباً يُضاف المعرف للقائمة ويُستدعى block() لتعليق العملية وتحويلها لحالة الانتظار فوراً دون حرق وقت المعالج.
• دالة signal(): تزيد العداد S.value++، فإذا ظل سالباً أو صفراً فهذا يعني وجود عمليات معلقة في القائمة، فيتم سحب عملية $P$ واستدعاء wakeup(P) لنقلها لطابور الجاهزية (Ready Queue).
ملاحظة امتحانية: القيمة المطلقة للعداد عندما يكون سالباً تمثل عدد العمليات المعلقة في طابور الانتظار بالضبط!

Classical Problems: The Readers-Writers Problem

المسائل الكلاسيكية: مسألة القراء والكتّاب (سؤال امتحاني متكرر)

📖 Rules & Shared Variables القواعد والمتغيرات المشتركة

A shared database or file accessed by concurrent readers and writers:

ملف أو قاعدة بيانات مشتركة تصل إليها عمليات قراءة وكتابة:

  • Readers: Only read data; multiple readers may access concurrently. القراء: يقرؤون فقط، ويُسمح لعدة قراء بالقراءة معاً في نفس اللحظة.
  • Writers: Read and modify; requires exclusive mutual access (no other writer and no readers allowed). الكتّاب: يعدلون البيانات، ويشترط وجود كاتب واحد فقط بمفرده تماماً.
  • Shared Data:
    semaphore rw_mutex = 1; (protects database for writers)
    semaphore mutex = 1; (protects updates to read_count)
    int read_count = 0; (tracks active readers)     المتغيرات المشتركة: سيمافور rw_mutex = 1 لحجز الملف، سيمافور mutex = 1 لحماية العداد، ومتغير read_count = 0 لحساب القراء.

✍️ Reader & Writer Implementation Code كود تنفيذ القارئ والكاتب

// Writer Process do { wait(rw_mutex); /* writing is performed */ signal(rw_mutex); } while (true); // Reader Process do { wait(mutex); read_count++; if (read_count == 1) wait(rw_mutex); // First reader locks out writers signal(mutex); /* reading is performed */ wait(mutex); read_count--; if (read_count == 0) signal(rw_mutex); // Last reader frees writers signal(mutex); } while (true);
📌
Midterm 2022 Question 5 Full Breakdown تحليل تفصيلي شامل لسؤال ميدتيرم 2022 (المسألة الخامسة) Midterm 2022 Q5

Sub-question 1: Initialization
➔ readCount = 0; mutex = 1; writeBlock (rw_mutex) = 1;

Sub-question 2: Suppose a writer is updating, and 3 new readers arrive. Where are they blocked?
➔ Reader 1: Successfully acquires mutex, increments readCount to 1, and calls wait(writeBlock). Since the writer holds writeBlock, Reader 1 blocks on the writeBlock semaphore queue.
➔ Reader 2 & Reader 3: Arrive while Reader 1 is blocked inside its entry section before calling signal(mutex). Therefore, Reader 2 and Reader 3 block on the mutex semaphore queue!

Sub-question 3: Suppose some readers are reading. What happens to a newly arrived writer?
➔ The writer invokes wait(writeBlock). Because the first reader previously acquired writeBlock, the writer finds writeBlock == 0 and is blocked on the writeBlock semaphore queue until the last reader decrements readCount to 0 and invokes signal(writeBlock).

Sub-question 4: Are writers subject to starvation in this solution? Justify.
➔ YES! In this first readers-writers solution, readers are prioritized. If new readers keep arriving while active readers are reading, readCount never drops to 0. Consequently, signal(writeBlock) is never called, causing the writer to starve indefinitely!

الفقرة 1: التهيئة الابتدائية
➔ readCount = 0; mutex = 1; writeBlock = 1;

الفقرة 2: إذا كان الكاتب يكتب ووصل 3 قراء، أين تُحجز كل عملية؟
➔ القارئ الأول: ينجح في تجاوز wait(mutex) ويزيد العداد لـ 1، ثم ينفذ wait(writeBlock). وحيث أن الكاتب يحجز الملف، يُحجز القارئ الأول في طابور انتظار السيمافور writeBlock.
➔ القارئ الثاني والثالث: يصادفان أن القارئ الأول معلق قبل أن ينفذ signal(mutex)، وبالتالي يُحجز القارئان 2 و 3 في طابور انتظار السيمافور mutex!

الفقرة 3: ماذا يحدث لكاتب وصل أثناء قراءة بعض القراء؟
➔ يستدعي الكاتب wait(writeBlock) فيجد القيمة 0 (لأن القارئ الأول حجزها)، فيتم تعليق الكاتب في طابور writeBlock حتى ينتهي آخر قارئ تماماً ويصفر العداد ويطلق الإشارة.

الفقرة 4: هل يعاني الكتّاب من التجويع (Starvation)؟ ولماذا؟
➔ نعم! لأن الأولوية للقراء؛ فإن استمر تدفق قراء جدد فلن يصل readCount للصفر أبداً، ولن يتم استدعاء signal(writeBlock)، مما يجعل الكاتب ينتظر لأجل غير مسمى.

The Bounded-Buffer & Dining Philosophers Problems

مسألة المخزن المحدود وفلاسفة العشاء

📦 Bounded-Buffer with Semaphores المخزن المؤقت المحدود بالسيمافورات

Pool of $n$ buffers, each holding one item:

مخزن يتسع لـ $n$ من العناصر، وتُدار بالسيمافورات الثلاثة التالية:

  • semaphore mutex = 1; (Mutual exclusion for buffer access) mutex = 1 للاستبعاد المتبادل أثناء إضافة أو سحب عنصر.
  • semaphore full = 0; (Counts full buffer slots available for consumer) full = 0 لحساب عدد الخانات الممتلئة المتاحة للمستهلك.
  • semaphore empty = n; (Counts empty buffer slots available for producer) empty = n لحساب عدد الخانات الفارغة المتاحة للمنتج.
// Producer do { // produce item wait(empty); wait(mutex); // add item to buffer signal(mutex); signal(full); } while (true); // Consumer do { wait(full); wait(mutex); // remove item from buffer signal(mutex); signal(empty); // consume item } while (true);

🍽️ Dining-Philosophers & Deadlock مسألة الفلاسفة وتجنب الجمود (Deadlock)

Five philosophers alternate between thinking and eating from a shared bowl, requiring two chopsticks ($i$ and $(i+1)\%5$):

5 فلاسفة يتناوبون بين التفكير وتناول الطعام، ويحتاج كل فيلسوف لعودين ($i$ و $(i+1)\%5$):

  • Naive Solution: Each philosopher executes wait(chopstick[i]); wait(chopstick[(i+1)%5]); الحل الساذج: كل فيلسوف يلتقط العود الأيمن ثم الأيسر.
  • Deadlock Hazard: If all 5 philosophers become hungry simultaneously and grab their right chopstick, all chopsticks become 0 and every philosopher blocks waiting for the left chopstick indefinitely (Deadlock!). خطر الجمود (Deadlock): إذا جاع الفلاسفة الخمسة معاً والتقط كل منهم عوده الأيمن، يحدث جمود متبادل ويتوقف الجميع للأبد!
  • Remedies: Allow at most 4 philosophers at the table, pick up chopsticks only if both are available, or use asymmetric odd/even philosopher rules. الحلول: السماح لـ 4 فلاسفة كحد أقصى بالجلوس، أو اشتراط توفر العودين معاً قبل الالتقاط، أو التناوب غير المتماثل (فردي/زوجي).

Chapter 5 Key Terms & Exam Glossary

قاموس المصطلحات والمفاهيم الأساسية للفصل الخامس

Race Condition
حالة التسابق (Race Condition)

A concurrent execution anomaly where the final outcome depends on the nondeterministic execution order of accessing shared data.

خلل في التنفيذ المتزامن تتوقف فيه النتيجة النهائية على الترتيب العشوائي للوصول إلى البيانات المشتركة.

Critical Section
القسم الحرج (Critical Section)

A code segment accessing shared resources that must be executed under mutual exclusion to maintain data consistency.

جزء من كود البرنامج يعدل موارد مشتركة ويجب تنفيذه تحت مظلة الاستبعاد المتبادل لمنع فساد البيانات.

Counting vs. Binary Semaphore
السيمافور العددي مقابل الثنائي

Counting semaphores range over unrestricted domains; binary semaphores range only between 0 and 1 (acting as mutex locks).

السيمافور العددي يتخذ أي قيمة صحيحة لتمثيل الموارد المتاحة؛ بينما الثنائي قيمته 0 أو 1 فقط ويعمل كقفل متبادل.

Busy Waiting / Spinlock
الانتظار العاطل / قفل الدوران

A mechanism where a process loops continuously on the CPU while waiting for a lock, wasting valuable processor cycles.

آلية يدور فيها المعالج في حلقة فارغة بانتظار فك القفل مما يهدر طاقة ووقت المعالج.

Deadlock
الجمود الميت (Deadlock)

A situation where two or more processes wait indefinitely for an event that can be caused only by one of the waiting processes.

حالة تتوقف فيها عمليتان أو أكثر بانتظار حدث لا يمكن أن يسببه إلا إحدى العمليات المتوقفة نفسها.

Priority Inversion
انعكاس الأولوية (Priority Inversion)

A scheduling anomaly where a higher-priority process is blocked waiting for a lock held by a lower-priority process (solved via Priority Inheritance).

خلل في الجدولة تتعطل فيه عملية عالية الأولوية لانتظارها قفلاً تحتجزه عملية منخفضة الأولوية.
